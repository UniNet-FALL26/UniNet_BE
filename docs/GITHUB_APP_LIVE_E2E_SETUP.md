# GitHub App live E2E — Step 6A preparation

Status: preparation only. No real GitHub App authorization, webhook delivery, migration rollout or live E2E has been performed. Do not start Step 6B without separate approval.

## Isolation and prerequisites

Windows, .NET SDK, Docker Desktop, ngrok, a dedicated GitHub test account or organization and test repositories are required. The new launcher is pinned to `E2E`, `http://localhost:5239`, local PostgreSQL `127.0.0.1:55433`, container `uninet-step2-concurrency`, and the separate database `uninet_github_app_e2e`. The database must be new and confirmed disposable; do not point it at `uninet_e2e` or another database with data to retain. The checker does not create databases or apply migrations. First inspect the Docker container and port mapping and independently confirm the database name is unused; create it only as an explicitly disposable test target. Verify `SELECT current_database()`, `__EFMigrationsHistory`, source migration IDs, drift, backup and downgrade constraints before separately authorizing a migration. In particular, review the historical authorization-flow quarantine migration and retain its data. See [deployment rollout checklist](./GITHUB_APP_DEPLOYMENT_CONFIGURATION.md).

Copy [.env.github-app.e2e.example](../.env.github-app.e2e.example) to the Git-ignored `.env.github-app.e2e`. Fill all placeholders locally; do not share the file or values. Use an absolute PEM path outside the repository, an existing private absolute key-ring directory, and a PFX with RSA private key outside the repository. Restrict Windows ACLs to the test user/service. The test key ring must persist across restarts. A shared ring, matching application discriminator and retained old keys/PFX certificates are needed for multi-instance use and certificate rollover. Never replace an existing production or E2E ring: old ciphertext requires its original keys and certificates. The application retains purpose `UniNet.GitHubOAuth.Token.v1`; OAuth credentials and App user credentials remain separate records.

The operator supplies App ID, App client ID/secret, App PEM, App webhook secret, separate legacy OAuth App client ID/secret and legacy webhook secret, JWT key, local PostgreSQL password, callback/return URLs and PFX password where required. Installation ID is discovered through the authorized user's installation API and is not a startup setting or trusted browser proof. Choose GitHub accounts and test repositories owned by or explicitly available to the test user; the connecting GitHub user must have both repository admin and read permission, while UniNet requires Creator or authorized Git Manager. Installation read access alone does not prove the user's admin permission.

## GitHub App and ngrok settings

1. Start `ngrok http 5239` and obtain its HTTPS origin from the ngrok UI. Set that origin in the local template. A changed tunnel hostname requires updating both local callbacks and GitHub registrations.
2. In GitHub Developer Settings register a dedicated test GitHub App. Homepage: an operator-controlled HTTPS page; it is distinct from all callbacks. User authorization callback: `https://<tunnel>/api/github/app/authorization/callback`. Shared webhook URL: `https://<tunnel>/api/webhooks/github/app`, with its own App webhook secret. The optional installation setup URL is a different GitHub feature; this backend does not expose a dedicated installation setup callback. Discover and verify installation through the App user flow instead of trusting `installation_id` from a redirect.
3. Configure the existing OAuth App separately with callback `https://<tunnel>/api/github/oauth/callback`. The App callback and OAuth callback must match their respective registered values exactly. Both configured return targets in this E2E template use an HTTPS allowlisted target. The template's Swagger URL is only a possible redirect destination, not a complete frontend OAuth workflow; use a test client able to complete the existing OAuth flow.
4. App repository permissions: Metadata read (GitHub mandatory), Contents read (branches/commits and push), Pull requests read (PRs, reviews and review comments), Issues read (issues and issue comments). Releases use repository Contents read. These are read permissions; no repository write grant is required for backend syncing. Test-user admin authority is separately checked through GitHub user permissions. Public/private access depends on installation selection and the user's actual rights. No additional organization or account permission is identified by the current sync call paths; organization approval may be required by GitHub policy.
5. Subscribe to `push`, `pull_request`, `issues`, `issue_comment`, `pull_request_review`, `pull_request_review_comment`, and `release`; App installation lifecycle uses `installation` and `installation_repositories`. The consumer routes supported activity events into the existing sync pipeline. Branch create/delete events are not classified as supported activity events; scheduled polling/reconciliation covers state when a webhook is absent. Do not create repository-specific App webhooks.

GitHub documentation: [registering a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app), [setup URL and installation ID verification](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url), [permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app), [webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads).

## Preflight and start

Run `powershell -File .\scripts\check-github-app-e2e.ps1`. It checks the local config without printing values, URL syntax and routes, allowlisted DB target, the container mapping and database identity, source/history migration IDs, private paths and Git ignore. It does not verify GitHub registration, GitHub credentials, external tunnel reachability, DB login using the application's connection string, filesystem ACLs or PEM/PFX validity. Enabled startup performs cryptographic configuration validation; never treat a syntactic preflight as live readiness.

The existing Phase 3 launcher is not suitable here: it requires `uninet_e2e`, port 55432 and a relative key ring, while App-enabled startup requires an absolute existing ring and certificate. After explicit database/migration approval and a successful preflight, run `powershell -File .\scripts\start-github-app-e2e.ps1`; it loads the PEM into the child process environment and runs the isolated E2E backend. It refuses an occupied port and does not stop processes. Check `/swagger/index.html`, `/health/github/readiness`, `/health/github/instance`, and `/health/github/queue` after startup. Do not expose the local database through ngrok.

## Step 6B scenario checklist

All rows are NOT TESTED. Common preconditions: approved isolated database and migration history, App enabled, private persistent Data Protection ring, ready backend/worker, test users and repositories, real tunnel and authorized test GitHub App. For every row record UTC time, safe HTTP status, IDs, relevant database state, job/delivery status and sanitized health/logs; never record tokens, raw webhook payloads or private content. Common cleanup: retain evidence and history; stop only the test backend/tunnel when authorized; restore deliberately changed test App/repository settings. Do not delete Git history or databases as routine cleanup.
