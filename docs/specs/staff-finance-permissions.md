# Staff financial permissions and income-wallet withdrawals

## Objective and confirmed scope
Implement the approved role contract: Student=0, Partner=1, Assessor=2, Verifier=3, Moderator=4, Accountant=5, Admin=6. User approved implementation and requested this replacement table on 2026-11-01. Admin has every default permission; other roles can only perform their own functions. Permission overrides may restrict/restore permissions within a role, never grant another role's functions. Accountant performs financial work: view payments/reports, record documented wallet income, create/review refunds, review withdrawals, create payout orders and confirm completed manual bank transfers.

Migrate old Admin=2 to Admin=6, Moderator=3 to Moderator=4, and Verificator=4 to Assessor=2. Increment staff SessionVersion, revoke refresh tokens, update single-Admin index/check constraint and persisted broadcast audiences. Existing expert assignments stay attached to their original account/profile IDs. Verifier is the new identity-verification staff role; Assessor retains expert assignment/report/calendar responsibilities.

User confirmed: withdrawals use the user's income-wallet balance and transfers are manual bank transfers confirmed by accounting. There is no current wallet/withdrawal implementation. Checkout payments are expenses, never automatic income credits. Refund provider is currently ManualRefundProvider; approval must not fabricate a successful refund.

## Contracts and behavior
- Reuse NotificationPermissionPolicy, permission overrides, active-account/session checks, staff creation and Dashboard management UI. Add Finance to staff authorization gates where existing per-action permission checks apply; do not grant staff-management or permission-management rights to non-Admin staff.
- Financial permission keys: finance.view, finance.wallet.credit, finance.refund.create, finance.refund.review, finance.withdrawal.review, finance.payout.create, finance.payout.confirm, finance.report.export. Accountant/Admin receive these defaults; Admin can restrict each staff member individually. Public registration still accepts Student/Partner only. Verifier gets account identity reviews; Assessor gets expert evidence work; Moderator gets content moderation and user violation handling.
- Income ledger is append-only, in whole VND. Documented manual income credit requires amount, reason and unique source reference. Same source reference and identical payload returns the original credit; conflicting payload fails. Store credits and completed withdrawal debits; never modify a balance directly or credit a checkout charge as income. Only Student/Partner wallets are eligible.
- Available = ledger balance minus Requested/Approved/Ordered withdrawal reservations. Requests have a durable owner-scoped idempotency key and an immutable amount/bank-recipient snapshot. Identical retries return the original request, including terminal requests; changed payloads fail. User may cancel only a Requested withdrawal. Rejection before ordering/cancellation releases the reservation; payout confirmation posts exactly one debit.
- Withdrawal transitions: Requested -> Approved -> Ordered -> Paid; Requested/Approved -> Rejected; owner Requested -> Cancelled. Ordered cannot be ordinarily rejected or cancelled: money remains reserved while a transfer result is uncertain. Releasing an ordered reservation requires a separately designed reconciliation process proving no transfer occurred; that release operation is outside this initial implementation. Approval/order/confirmation require separate permissions, immutable actor/time audit and reasons/references where relevant. Actual transfer happens outside the app; confirmation records bank transaction evidence, never executes a bank API.
- Exactly one payout order per withdrawal, with immutable amount/recipient snapshots. A normalized bank transaction reference is unique within the paying bank account, whose identifier is recorded with the evidence. Confirmation atomically completes the order and withdrawal and appends the linked debit. Repeating identical confirmation returns the result; changed evidence or a reference already attached to another payout fails.
- New staff-created refund requests, including new requests through the existing Admin endpoint, require another authorized staff member to approve/reject. Pending approval reserves the payment balance and cannot be dispatched by the refund worker. Backfill only preexisting rows as approval-not-required at migration time; do not infer exemption from Admin/LegacyUnknown source for future requests. Existing automated system refund creation remains explicitly approval-not-required under its existing business rules. Approved refunds remain pending/manual until an actual refund result is reconciled; approval alone never means money returned.
- Centralize refund reservation rules for every creator, including deadline automation and the existing Admin endpoint. Include failed automatic timeout refunds that current business rules still reserve. Explicit review rejection releases only an undispatched approval-pending reservation. Gate both worker selection and direct ProcessAsync calls on approval; test existing automatic/manual behavior for regressions.
- Protect every backend read/mutation and frontend route/action. No self permission changes. Keep Admin-only account/staff protection. Lock per wallet/payment or use serializable transactions; conditional updates and unique keys prevent competing decisions, duplicate credits and duplicate debits. No private bank details in logs/public endpoints.
- Add /api/wallet owner APIs; /api/admin/finance for payment reporting, wallet credits, withdrawal operations and refund review. Return explicit bounded DTOs and paginated lists. Sensitive administrative responses are no-store.
- Dashboard: Finance login/role routes, capability-filtered finance pages and financial controls; staff role option and grouped permission editor. End-user app: Wallet link in Student/Partner Settings, balance/history, withdrawal request/cancel with clear reserved balance and status.
