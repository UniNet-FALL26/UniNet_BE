### Activity routing and scope

The existing [GitHubAppWebhookConsumer](../UniNet.Application/Services/GitHubAppWebhookConsumer.cs) now claims both lifecycle and repository-activity deliveries; [activity routing](../UniNet.Application/Services/GitHubAppWebhookConsumer.Activity.cs) handles the latter without introducing a second Activity pipeline. The existing App HMAC endpoint remains the sole ingress, and the consumer reloads/decrypts the persisted leased delivery and verifies its hash. It checks body installation/repository IDs against the stored metadata, validates the event's required top-level object/action shape, and does not use sender or repository name as authority. GitHub's [webhook event reference](https://docs.github.com/en/webhooks/webhook-events-and-payloads) describes these payloads.

Supported trigger names: `push` (requires `ref`), `pull_request`, `issues`, `pull_request_review`, `issue_comment`, `pull_request_review_comment` and `release`. For non-push events a nonempty signed action and appropriate event object(s) are required. Any such action triggers the same full provider scan; the payload is **not** converted directly into an Activity. `create`/`delete` branch events are Unsupported; branch state is fetched by existing sync and scheduled polling remains the fallback. A full scan cannot reconstruct an already-deleted GitHub object that the API no longer returns.

Before enqueue, routing requires the configured App ID, a JWT-verified App and active installation with the expected owner, a current non-revoked local grant for the immutable repository ID, a repository-scoped installation token and a live read check. A provider-verified repository rename/transfer refreshes existing repository metadata by stable ID before the worker uses its path. No OAuth or App user token is used. Missing/unknown/revoked/ambiguous scope is deferred through the bounded delivery retry policy; it is not falsely marked Processed. A verified grant with zero eligible project links is safely Processed with no jobs and no new link.

### Multi-project transaction and coalescing

Within a serializable transaction the consumer locks its delivery, acquires the installation's shared advisory lock, rechecks installation/grant versions and status, then calls the existing [GitSyncJobService](../UniNet.Application/Services/GitSyncJobService.cs) to enqueue one App-source `Webhook` job per active, unpaused, linked project association with the exact grant/repository. OAuth links, lost/paused/unlinked links and other installations are excluded. Delivery `Processed` and durable jobs commit together; an expired lease, concurrent revocation or database conflict leaves the delivery retryable and cannot commit partial jobs.

A Pending job is coalesced only while its job row is locked, so a concurrent worker claim cannot make an old scan appear to cover a new trigger. An already Running or RetryScheduled job gets at most one Pending follow-up; repeated deliveries coalesce into that follow-up. Per-project active-job constraints and the `app-webhook:<delivery-id>` idempotency key protect races/replay. App `Webhook` is the existing `GitSyncType`; the existing claim and [processor](../UniNet.Application/Services/GitHubSyncJobProcessor.cs) now accept that type and continue to revalidate scope, fetch provider pages, persist/checkpoint and grant Activity visibility independently per project.

Expired `Processing` leases are reclaimable; stale owners cannot commit. Unknown actions become `Unsupported`, not `Processed`. Failed rows and encrypted bytes are retained; an operational requeue/dead-letter workflow remains a deployment follow-up.

The consumer reloads the persisted leased row, decrypts and hashes the original bytes, and validates action, installation ID, App ID and owner identity. Configure numeric **`GitHubApp:AppId` / `GitHubApp__AppId`**, in addition to the existing App client ID, private key and distinct webhook secret. It checks the App JWT identity with GitHub's `/app` endpoint; active/suspended installation responses must also match the configured App ID and immutable owner ID. Missing App ID is a diagnosed retryable configuration error. No GitHub sender creates UniNet account ownership, project membership or links.

### Lifecycle and reconciliation

Supported `installation` actions are `created`, `deleted`, `suspend`, `unsuspend` and `new_permissions_accepted`; `installation_repositories` supports `added` and `removed`. These are the documented [GitHub App webhook actions](https://github.com/octokit/webhooks.js#webhook-events). GitHub may deliver events [out of order](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks#webhooks-deliveries-are-out-of-order); receive time alone is never treated as current permission evidence.

- Before a known installation is checked over the network, a short transaction fences it as verification-unknown, invalidates local cached tokens and schedules reconciliation. App authorization paths then defer while OAuth links remain untouched. A crash here leaves durable fail-closed state for lease/poll recovery.
- Confirmed active/positive events require App/installation identity verification. A verified `created` can add an installation; a verified `added` can add or restore repository grants by immutable GitHub repository ID. Neither creates a project link or UniNet account mapping. Access stays unknown until the existing full reconciliation and repository-scoped read check restore eligible links and enqueue reconciliation sync; no second Initial job is created.
- A signed `installation.deleted`, matching configured/JWT App ID and known owner, **plus** GitHub's installation 404 marks that known installation Uninstalled. A standalone ambiguous 404, 403, rate limit or provider outage never does. A stale deleted event with a currently active installation only schedules verification. A confirmed suspended installation is marked Suspended. Confirmed removal requires a complete current installation repository listing and absence of the affected IDs; a stale removal cannot revoke a currently present grant.
- Negative effects and delivery `Processed` are committed atomically: App-backed links become AccessLost, pending/retry jobs are canceled, and history/checkpoints/Activity are retained. Repeated events do not duplicate history. Lifecycle changes use the same installation advisory lock, serializable transactions and updated-state fencing as polling. Concurrent newer reconciliation causes retry instead of overwriting it.
- A lifecycle event whose installation is not local is not a basis to create project associations. An unknown `deleted` is a safe no-op. Other events may create an installation or grant only after verifying live App/owner/installation/repository evidence. Lifecycle payloads require the documented full installation `app_id` and account (`id`, `login`, `type`) plus repository ID arrays where applicable. A future unrecognized action is Unsupported.

### Endpoint, security and source isolation

`POST /api/webhooks/github/app` is an anonymous webhook endpoint authenticated by its configured HMAC-SHA256, not by a UniNet JWT. It reads the exact request bytes with a hard 10 MiB limit; `GitHubApp:MaximumWebhookPayloadBytes` defaults to 1 MiB and is capped by the hard limit. Configure the backend-owned `GitHubApp:WebhookSecret` (environment variable `GitHubApp__WebhookSecret`) uniquely for this App. The App endpoint rejects a secret equal to `GitHubWebhook:Secret`; it never tries the legacy secret. The existing OAuth/repository endpoint remains `POST /api/webhooks/github`; after authenticating its own secret it rejects App-shaped deliveries containing an installation object, so they cannot route into the legacy enqueue path. No raw body or secret is logged or returned.

[GitHubAppWebhookController](../UniNet.API/Controllers/GitHubAppWebhookController.cs) calls [GitHubAppWebhookService](../UniNet.Application/Services/GitHubAppWebhookService.cs) through [IGitHubAppWebhookService](../UniNet.Application/Interfaces/IGitHubAppWebhookService.cs). The App service reuses the existing constant-time `X-Hub-Signature-256` verification and parses JSON only after a valid signature. A distinct App secret identifies the configured App webhook; deployment must not share that secret with other Apps. GitHub signs the body, not the event/delivery headers. Step 4B handlers must validate the decrypted event/action schema and current installation/repository authorization again; a local scope match is a routing hint, not a provider authorization decision. See GitHub's [signature validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) and [event payload reference](https://docs.github.com/en/webhooks/webhook-events-and-payloads).

### Delivery contract and recovery

App and legacy deliveries have independent identity namespaces: App uses `GitHubAppWebhookDeliveries`, legacy keeps `GitHubWebhookDeliveries` and its existing unique constraint. A database unique constraint makes App insert atomic for concurrent redelivery. A reused delivery ID with different authenticated body or event is a 409 conflict. A successful 202 response contains only `duplicate`, `supportedEvent`, `route` and `status`; it means durable staging, **not** that a webhook event has been processed.

Supported lifecycle events: `installation` and `installation_repositories`; supported repository events: `push`, `pull_request`, `issues`, `issue_comment`, `pull_request_review`, `pull_request_review_comment`, `release`. Event/action are classified and stored, but actions are not executed. A matching local installation/link/grant is `PendingHandler`; missing/unverified/revoked/mismatched scope is `AwaitingScope`; other events including `ping` are `Unsupported`. Supported events require an installation ID, repository events require a repository ID, and non-push supported events require an action. No App activity, sync job, installation transition or project grant is created by this foundation.

The raw bytes are base64-encoded and protected with the existing GitHub Data Protection protector before storage; only the encrypted payload and SHA-256 digest are persisted. A failed encryption/database insert does not acknowledge a delivery or reserve its ID; the same ID can be redelivered in a fresh request. Pending rows survive process restart and retain the encrypted bytes, route, action, attempt and next-attempt fields for a future consumer. **There is no App handler, claim/lease executor or automatic failed-delivery redelivery in Step 4A.** GitHub does not automatically redeliver failed requests; an operator/test integration must request redelivery until Step 4B/operations provide a policy. `PendingHandler`/`AwaitingScope` are never `Processed`.

The existing Data Protection key ring must be persistent, shared between instances that receive/process deliveries, backed up and protected; otherwise encrypted pending bodies may become unreadable after restart or on another instance. No webhook payload/token belongs in logs, APIs, migration scripts or documentation.

### Durable verification and backoff

[Installation persistence](../UniNet.Domain/Entities/GitHubAppInstallation.cs) now stores `VerificationUnknown`, `NextReconciliationAt` and `ReconciliationFailures`. HTTP Retry-After (seconds/date) and exhausted-quota reset metadata are respected; the later provider deadline or exponential fallback is used. Failure count caps at 16; fallback caps at six hours. Polling continues at that bounded cadence so recovery remains automatic. No transaction or sleep spans GitHub network I/O; a connection holds the advisory lock and releases it on completion/disconnect.

Defaults under `GitHubSync`: `ReconciliationBatchSize=25`, `ReconciliationIntervalMinutes=15`, `ReconciliationTimeoutSeconds=30`, `ReconciliationPollSeconds=60`. Values are clamped in runtime. The existing [hosted worker](../UniNet.API/Services/GitSyncWorker.cs) owns both its processing loops and a managed reconciliation loop; no additional hosted worker exists. Long sync jobs cannot monopolize the reconciliation loop. Disabled sync makes no reconciliation calls. Pagination remains bounded at 1,000 pages and incomplete/inconsistent results never revoke grants.

| Evidence | Persisted behavior |
| --- | --- |
| Verified active installation + complete repository list | Clear unknown, synchronize existing grants, schedule next check; restoration still requires a fresh repository-scoped read check |
| Confirmed suspension / complete list omitting a repository | Record known state/grant revocation, atomically mark affected active App links AccessLost and cancel pending/retry jobs; retain data/history |
| Ambiguous 401/403/404, rate limit, timeout, malformed/incomplete response or temporary failure | Set unknown and durable deadline; retain the last known status, grants, Activity and checkpoints; do not invent an uninstall |

While unknown, App linking/grant mutation, activation, recovery, manual/scheduled enqueue, claim, resume and processor eligibility all fail closed or defer. Status/listing responses use the additive `VerificationPending` readiness value. This is not a request for user OAuth reauthorization. Pending jobs remain durable but cannot run until verification succeeds. OAuth branches are unchanged. Shared token caches cannot bypass database eligibility checks on another instance.

### Transaction and race handling

- Claim now obtains a shared transaction advisory lock and checks eligibility again in a fresh statement before committing its App claim. It rolls back if reconciliation holds the exclusive lock or the grant/source changed. This closes the pre-revoke statement-snapshot window.
- Reconciliation uses serializable persistence after provider calls and compares the installation and grant observations captured before those calls. A concurrent authorization update/revoke supersedes stale restoration evidence.
- Revoke updates grants, affected project links, history and queued jobs in one transaction. Manual/scheduled enqueue and recovery use existing serializable transactions and active-job constraints. Serialization/deadlock conflicts are controlled retries; simultaneous recovery cannot add a second Initial job or duplicate Scheduled jobs.
- A job claimed before a committed revoke is rejected at the processor's next authorization boundary. History and project visibility are retained.

## Decision and existing components

A GitHub App is the intended route: it has an application-level webhook and installation tokens scoped to installation-selected repositories and app permissions. OAuth Apps require per-repository webhook management and appropriate webhook scope plus repository admin access; uninstalling an OAuth token does not automatically remove webhooks. See [GitHub's comparison](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps) and [webhook authorization](https://docs.github.com/en/webhooks/types-of-webhooks).

The current implementation already has account OAuth, project creator/manager authorization, provider repository metadata, project links, initial jobs, scheduled sync, webhook HMAC/deduplication, activity visibility, leases and checkpoints. Reuse these components. Current `GitSyncJob` and `ProjectGitRepository` require an OAuth connection: installation-backed links cannot safely run until credential selection, worker eligibility, authorization and reconciliation are redesigned together. Existing repository linking returns 409 for an active duplicate; an idempotent onboarding operation should be additive and should not silently alter that existing contract.

## Trust model and minimal persistence proposal

- **GitHub account identity:** verified provider user ID; project Git Identity remains separately owned and project scoped.
- **OAuth connection:** existing OAuth App credential. A GitHub App user access token is a separate credential issued by that App and must not be confused with the existing OAuth App token.
- **App installation:** stable GitHub installation ID, owning GitHub account ID/type, status, permissions and last verified timestamp. Shared across projects; never store installation private key per installation.
- **Account-to-installation authorization:** separately persist verified association between UniNet account / GitHub App user authorization and installation. A submitted installation ID or installation webhook alone proves no user entitlement. GitHub explicitly warns that setup `installation_id` can be spoofed; verify via the authenticated GitHub App user token and installation endpoints. [GitHub setup URL](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url).
- **Repository access grant:** installation ID + stable provider repository ID, status and verification time, scoped to an authorized user selection and installation. Actor authorization must additionally be checked against the user's access to the repository, not just the installation's access.
- **Project repository link:** project association referencing a verified installation/repository grant, with its own access state, history and visibility boundary. Existing OAuth links remain valid. Exactly one credential mode per link/job must be enforced with database constraints; avoid guessing whether OAuth or installation applies.
- **Installation setup flow:** persist single-use hashed state, account/project binding, return-target key, expiry and status. Do not trust arbitrary return URLs, claimed installation IDs or organization approval status without provider verification.

Migration(s) must add these relationships and constraints without modifying existing migration IDs or applying migrations to shared databases. Job claim, processor, repository status, scheduled reconciliation and history need explicit installation-aware credential handling; tokens are short lived and are never sent to clients, logs or database as plaintext. Provider objects remain shared while project visibility and history cutoffs remain separate.

## Proposed API and event behavior

1. An authenticated creator/manager requests onboarding status for a project. Reuse an eligible existing connection/authorization only when the required GitHub App user authorization and installation are verified.
2. Start installation/authorization with account- and project-bound state. After callback validate state once, exchange the app user authorization, and re-check installation ownership, user access, app identity and organization approval with GitHub. Pending organization approval is not usable access.
3. List repositories at the intersection of user access and installation scope, with pagination and explicit permissions. Confirming selection performs another access check, then atomically creates/reuses the project link and one initial sync job. Repeat confirmation returns the same link; unique constraints and concurrency recovery enforce this.
4. The shared App webhook validates HMAC before parsing and records delivery IDs. Only route repository events to links whose own verified installation grants include that repository. Apply `installation` and `installation_repositories` lifecycle events idempotently, including suspend/uninstall and repository removal. Reconcile provider state after ambiguous/out-of-order events; do not infer deletion from 404. Never expose payloads or secrets.
5. When access returns, verify it before restoring each affected association and enqueue reconciliation; preserve observation cutoff boundaries. Unlink only the project association, never remove a shared installation or App webhook. Rate limiting and temporary failures do not mark access lost.
